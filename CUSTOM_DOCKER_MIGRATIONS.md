# Custom Docker Image — Migration Switch Guide

This branch (`custom_energy_tracking_docker`) contains committed migration files
that are normally generated by CI after merging to `main`. They exist here so the
Docker image can be built with the correct schema embedded.

## Switching to the Official Image

When both feature branches merge to `main`, CI will auto-generate "official"
migrations with **different timestamps** (and possibly different tag names/numbers)
but **identical SQL content**. The hashes will match since they're SHA-256 of
the SQL content.

Drizzle's migration tracker uses **only `created_at` (the timestamp)** to decide
which migrations to run — it compares the journal's `when` values against the
last recorded row in `__drizzle_migrations`. The `hash` column is stored but
never checked.

### Steps

1. **Wait for both branches to merge** and CI to generate official migrations.

2. **Get the official timestamps** from the committed `_journal.json` files
   on `main` (or from the embedded journal in the official image's logs).

3. **Update the migration tracker** in your database:

   ```sql
   -- View current state
   SELECT id, hash, created_at FROM __drizzle_migrations ORDER BY created_at;

   -- Update timestamps to match the official journal
   -- Replace <your-timestamp> and <official-timestamp> with actual values
   UPDATE __drizzle_migrations
   SET created_at = <official-timestamp>
   WHERE created_at = <your-timestamp>;
   ```

   For SQLite, update two rows:
   - `created_at = 1779614789206` → set to official `add_updated_at_to_request_usage` timestamp
   - `created_at = 1779614914892` → set to official `add_provider_energy_details` timestamp

   For PostgreSQL, update two rows:
   - `created_at = 1779614789731` → set to official `add_updated_at_to_request_usage` timestamp
   - `created_at = 1779614915422` → set to official `add_provider_energy_details` timestamp

4. **Switch to the official Docker image.** The official image will see that
   its migrations have already been applied (timestamps match) and skip them.

### If Something Goes Wrong

If the official image tries to re-run migrations after the timestamp fix,
the Plexus codebase has **idempotent migration repair** logic that handles:
- SQLite `already exists` errors (tables/indexes created outside the migration system)
- Duplicate column errors (columns added outside the migration system)

So in the worst case, the migrations will be re-applied idempotently and the
duplicate entries in `__drizzle_migrations` won't cause a crash — but it's
cleaner to fix the timestamps upfront.
